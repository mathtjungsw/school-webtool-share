## 쓰기 주체와 외부 연결

사용자가 **“내부 원본은 업무도우미에서만 수정”**한다고 답했다. 별도 시트 직접 편집·외부 자동화가 있다는 가정을 작업 전제로 두지 않는다. 외부 입력 시트는 이 답변의 대상에서 제외했다.

- 운영 Apps Script의 현재 로그인 계정 트리거 화면: **0개**. 소스에 `onOpen/onEdit/onChange` 및 설치형 트리거 생성 호출도 없었다. 다른 계정이나 다른 프로젝트의 트리거까지 전부 없다고 단정하지 않는다. Google은 계정 간 설치형 트리거가 서로 보이지 않을 수 있다고 설명한다. [공식 트리거 제한](https://developers.google.com/apps-script/guides/triggers/installable)
- [외부 연결 메타데이터](2026-11-13-source-metadata.json): 주간계획, 창체, 등교지도, 급식지도, 실시간 출결, 기본 비공개 자료집 포인터를 읽기 전용으로 확인했다.
- 외부 주간계획·지도 등의 작성과 소유권·공개 범위를 변경하지 않았다. 실시간 출결 본문과 자료집 파일을 내보내거나 Firebase에 복사하지 않았다. 출결 파일의 권한 목록은 이 계정에 노출되지 않아 `null`로 남겼다.
- 외부 입력 시트의 실제 행 수·가공 결과 해시, 자료집 ScriptProperty의 사용자 지정 포인터 및 개별 파일 연결은 아직 조사하지 않았다. 이번 내부 원본 백업에 포함된 것으로 취급하지 않는다.

## 변경 추적 코드 준비

[쓰기 경로 조사](2026-11-13-write-path-audit.json)는 `Code.gs`와 `StaffAuth.gs`를 정적으로 분석했다. 실제 업무 함수를 실행하지 않는다.

- 시트를 직접 변경할 수 있는 유효 함수 33개, ScriptLock을 사용하는 함수 13개를 확인했다. 자체·하위 호출에 잠금이 없는 23개 후보에는 상위 함수가 잠근 뒤 호출하는 공통 도우미도 포함되므로, 이를 곧바로 23개 결함이라고 해석하지 않는다.
- `updateStaffChecklist_` 등 명시적인 변경뿐 아니라 `ensureSheets_`, 공지 정리, 명렬 보정, 조회 중 1회 명렬 보정까지 추적 경계에 넣어야 한다. `getSyncManifest_`의 버전 속성 기록은 자료 변경과 구분한다.
- `replaceSheetRows_`가 두 번 선언되어 있다. 현재 실제로 사용되는 뒤쪽 정의를 기준으로 조사했고, 기존 동작을 바꾸거나 중복 함수를 임의 삭제하지 않았다.
- `MigrationJournal.gs`를 추가했다. 공통 잠금의 중첩 획득을 방지하고, 권한 재검사 → 새로운 작업의 업무 검증 → 의도 기록/재조회 → 원본 저장/flush → 보존된 결과 참조와 완료 기록 순서를 정의한다.
- 같은 작업 ID·같은 요청은 완료 영수증을 재사용한다. 다른 내용의 재사용은 거부한다. `PREPARED`로 남은 작업은 원본을 확인하기 전 자동 재실행하지 않는다. 원본 저장이 확정된 뒤 후속 기록에 실패하면 원래 성공 값을 유지하고 `SOURCE_SAVED_TRACKING_PENDING`으로 구분한다.
- 요청 본문·이름·비밀번호·토큰을 의도 기록에 보관하지 않는다. 향후 어댑터는 인증정보를 제외한 업무 값으로 `requestHash`를 계산해야 한다. 중첩된 비밀번호·토큰 키가 있는 결과나 큰 결과는 완료 기록에 저장하지 않는다. 저장 실패 원문도 노출하지 않는다.

**실제 저널 저장 어댑터, 운영 action 연결, 영구 ID 대응표, 변경 후 불변 자료 저장, 복제 작업자, 보정/복구 화면은 아직 구현·연결하지 않았다.** `snapshotRef`는 검증된 불변 자료를 가리켜야 하는 인터페이스이며, 지금 실제 불변 자료가 만들어진다는 뜻이 아니다. 기존 13개 잠금이 공통 잠금으로 바뀐 것도 아니다. 구버전 요청에 서버가 새 작업 ID를 발급할 때의 중복 판정 한계도 연결 단계에서 다룬다.
