# 저널 변경분 복제와 불확실 작업 복구

2026-11-13. 사용자의 다음 단계 진행 지시에 따라 순차 복제·중단 후 재개·명시적 확인 기반을 구현하고 실제 합성 Google Sheets→Firestore 시험까지 완료했다. **실제 학교 자료는 복제하지 않았으며 운영 조회·저장 기준은 시트다.** PC·모바일도 현재 시트를 사용한다.

## 구현한 동작

- `MigrationReplication.gs`는 추적이 활성화된 원본만 받는다. 공통 잠금 안에서 미확정 작업이 없는 기준 시점의 사본을 고정하고, 그 이후 저널 revision을 순서대로 복제한다. 기준 사본은 별도 보존한 초기 조사 백업과 다르다. 실제 학교 기준 시점 R0는 아직 잡지 않았다.
- 기준 사본 및 변경분은 비공개 시트의 압축 본문에 고정하고 해시로 참조한다. Firestore 경로는 `schools/{scope}/replicaEpochs/{baselineRef}/operations/r{revision}/pages/p{index}`다. 페이지는 최대 50개 항목·약 220KB 기준으로 분할한다. 단일 항목 210KB·계획 1,024페이지를 넘으면 명시적 오류다. 저장 시 어댑터의 실제 요청 크기 검사도 적용한다.
- 페이지와 진행 지점을 함께 저장하고, 별도 읽기로 페이지 해시·건수를 확인한 뒤 다음으로 진행한다. 전 페이지 확인이 끝나야 작업 완료와 전역 revision을 하나의 조건부 commit으로 확정한다. `updateTime` 비교 조건으로 경쟁 실행의 덮어쓰기를 막는다. Firestore commit의 원자적 적용은 [공식 REST 문서](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases.documents/commit)를 따른다.
- 저장 후 응답이 유실되어도 이미 저장한 페이지·완료 지점을 읽어 이어 간다. 다른 실행이 먼저 완료한 상황도 다시 확인한다. 불확실한 `PREPARED`/`REVIEW_REQUIRED` 작업에서는 전역 복제를 멈추며, 기록 예약 후 원본을 쓰지 못한 빈 번호는 재사용하지 않고 빈 변경으로 넘긴다.
- `MigrationRecovery.gs`는 검토 계획 생성과 명시적 확인 함수다. 불확실 작업 이후 같은 자료를 수정한 첫 작업의 **변경 전 사본**을 사용해 해당 시점의 결과를 얻는다. 후속 작업이 없을 때만 현재 원본을 사용한다. 확인 전 원본·저널 번호·해시가 달라지면 오래된 계획을 거부한다.
- `ACCEPT_OBSERVED_SOURCE` 결정은 관측한 실제 상태를 복제 대상으로 확정한다. 원본 요청 재실행·원본 덮어쓰기·업무 성공 판정·성공 응답 생성·자동 원상 복구가 아니다. 원래 저널은 보존하고 확인 근거를 별도 불변 기록으로 남긴다. 운영 관리자 인증/API/화면 연결 전에는 비공개 내부 함수로만 존재한다.
- `MigrationStore.gs`에 revision 직접 읽기와 해시 기반 참조 인덱스를 추가했다. 기존 gzip MIME 수정은 유지한다. 관리자 수동 집계는 별도 확인된 작업을 미확정 오류와 구별하며, 일반 요청에서는 전체 저널 집계를 하지 않는다.

## 비용과 실행 범위

복제 실행은 기본 8단계·45초, 최대 40단계·180초의 단계 사이 예산으로 제한한다. 이미 진행한 곳부터 재개하며 새 변경이 없으면 Firestore 쓰기는 0건이다. 한 단계의 외부 요청이 예산보다 길어질 수 있으므로 강제 종료 시간 보장은 아니다. 네트워크·경쟁 충돌은 재시도 상태로 반환하며 반복 대기·자동 스케줄러는 설치하지 않았다.

일반 복제 실행에서는 전체 Firestore 목록이나 학교 원본 본문 전체를 반복 조회하지 않는다. 필요한 고정 페이지·변경 자료의 기록만 읽고, 한 실행 안에서 불변 메타데이터를 재사용한다. `migrationReadReplica_`는 별도로 실행하는 **전수 검증용**이며 사용자의 일반 새로고침 경로가 아니다.

원본 변경 전 사본·복제 페이지·진행 문서가 누적되므로 저장량과 읽기/쓰기가 증가한다. 이번 수치는 합성 시험 어댑터 관측값이며 실학교 운영량·과금 추정이 아니다. 무료 운영을 보장하지 않고, 비용 조사를 매 개발 단계의 중단 조건으로 삼지 않는다. Spark 및 기존 접근 제한을 유지했다. `pages.entries`, `operations.descriptor`, `replicaEpochs.resources`의 불필요한 인덱스 제외 선언은 로컬에 추가했으며 **실제 Firebase 설정에는 아직 반영하지 않았다.** 실제 자료 복사 준비 때 적용한다.

## 남은 연결과 다음 단계

현재 저장 구조는 검증 가능한 순차 복제 기록이다. 앱이 필요한 교사·날짜·자료 범위만 읽는 Firestore 조회용 구조와 백엔드 전환은 아직 연결하지 않았다. 전수 검증 함수로 앱의 매 조회를 대체해서는 안 된다. 확인 계획은 후속 최대 1,000개 revision, 전수 검증은 기준 이후 최대 10,000개 revision을 대상으로 하므로 운영 이력 누적에 맞는 체크포인트·보존/정리 설계도 남아 있다. 자동 정리·삭제·상시 감시를 구성했다고 보고하지 않는다.

다음은 운영 설정·관리자 수동 실행/확인·복제 진행 상태를 연결하고 운영 활성화 절차를 검증하는 작업이다. 현재 관리자 화면의 `replicaConnected:false`는 유지했으며 실제 운영 복제 진행을 표시한다고 주장하지 않는다. 기존 코드로 시작한 실행이 끝나는 경계와 추적 활성화를 준비한 뒤 [배포 규칙](../../AGENTS.md)에 따라 보호된 데스크톱 변경을 main에서 검토·검증하고 기존 고정 배포를 갱신한다. 가드를 우회하거나 새 배포 주소를 만들지 않는다.

그 이후 실제 원본의 R0 고정·초기 복사·변경분 복제와 PC/모바일 응답 및 권한 대조를 진행한다. 최종 전환/복구 리허설과 완전 동기화 검증 보고 후 사용자의 전환 지시를 받아 조회·저장 기준을 바꾼다. 현재 운영 비밀번호·세션·외부 입력 시트·실시간 출결 연결은 그대로다.
