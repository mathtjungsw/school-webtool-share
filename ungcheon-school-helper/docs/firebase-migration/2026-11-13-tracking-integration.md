# 변경 기록 저장소와 업무 저장 경로 연결

2026-11-13. 사용자의 다음 단계 진행 지시에 따라 개발 브랜치에 실제 Sheets 변경 기록 어댑터와 업무 경로 연결을 구현했다. **로컬 검증 완료 / 분리된 Google Sheets 시험의 추가 권한 승인 대기 / 운영 미배포** 상태다. 학교 자료를 Firestore에 복제하거나 조회·저장 기준을 전환하지 않았다.

## 구현과 보존 범위

- `MigrationStore.gs`: 원본과 같은 비공개 문서에 숨김 메타·저널·압축 본문·고정 UUID 대응표를 저장한다. 숨김 자체는 보안 경계가 아니며 문서 접근 권한을 따른다. 초기화·활성화는 자동으로 수행하지 않는다.
- revision 번호를 먼저 영속화하고 변경 의도와 해당 자료의 변경 전 상태를 확인한 뒤 원본을 수정한다. 예약 도중 실패한 번호는 빈 번호로 남겨 재사용하지 않는다. 미확정 작업은 자동으로 원본에 재적용하지 않는다.
- `MigrationCapture.gs`: 변경되는 자료 종류만 읽고, 저장 이후 변경 행·순서 및 삭제표식을 기록한다. 매 저장마다 전체 학교 DB를 내려받지 않는다. 복구를 위한 변경 전 사본은 해당 자료 전체이므로, 대량 시간표 교체에서는 해당 시간표만큼 저장량·Sheets 처리량이 증가한다. 실제 지연 시간과 누적 저장량은 아직 측정하지 않았다.
- 기존 ID가 없는 자료는 자연 키의 해시와 영속 UUID를 대응시킨다. 이름이나 행 번호를 문서 ID로 쓰지 않는다. 내용 수정·행 이동은 UUID를 유지하지만 자연 키 자체가 바뀌면 삭제/신규 생성으로 취급한다. 사람의 이름 변경을 동일인으로 추론하지 않는다. 중복 키·대응표의 UUID 중복은 중단하고 확인 대상으로 남긴다.
- `MigrationTracking.gs`: 인증 후 공통 잠금, 첫 실제 변경 직전 기록 예약, 원본 보존, 저장 결과 수집을 연결했다. 구식 내부 잠금은 같은 실행의 공통 잠금을 공유한다. 추적 활성화 후 직접 편집기 실행이나 미연결 경로의 쓰기는 조용히 우회하지 않고 거부한다.
- `Code.gs`의 내부 원본 접근 31곳과 기존 잠금 13곳을 명시적 접근 함수로 연결했다. 정적 조사 대상 실제 쓰기 함수는 33개다. 원래 중복 선언된 `replaceSheetRows_`는 마지막 선언을 기준으로 조사했으며 중복 선언을 별도로 정리하지 않았다. [이번 정적 조사](write-path-audit-stage3.json)는 실행 검증과 구분한다.
- 원본 저장 성공 후 변경 기록 완결에 실패하면 기존 성공 응답을 유지하고 영속 `PREPARED`를 남긴다. 일부 원본 수정 후 업무 오류가 반환되면 `REVIEW_REQUIRED`다. 둘 다 확인 전 자동 재적용하지 않는다. 부분 쓰기 자체를 원상 복구하는 기능은 아직 구현하지 않았다.
- 완료된 동일 요청은 저장된 응답으로 반환한다. 재요청에서도 직원 인증과 필요한 관리자·NEIS 기기 인증을 다시 검사한다. 토큰 발급 응답과 비밀번호는 저널 본문에 넣지 않는다.
- PC `hubRequest`가 업무 변경 요청에 `operationId`를 붙인다. 기존 체크리스트 `requestId`와 명시적으로 전달된 `operationId`를 보존한다. 조회·로그인 요청에는 새 ID를 붙이지 않고 입력 객체도 수정하지 않는다. 자동 재전송은 추가하지 않았다. 별도 호출로 새 요청을 만드는 수동 재시도는 같은 ID가 보장되지 않으며, 구버전 앱의 서버 생성 ID에도 같은 한계가 있다.
- 관리자 현황은 활성화된 경우 실제 기록·확인 필요 건수를 보여 준다. 아직 복제되지 않은 상태를 명시하며 기록 번호를 동기화 완료로 표시하지 않는다. 일반 조회에서 전체 저널을 스캔하지 않고 관리자 수동 확인에서만 집계한다.

PC와 모바일은 최종 전환 후에도 기존 Apps Script 주소·로그인을 유지하고 Apps Script가 Firestore를 조회한다. 현재 둘 다 시트 원본을 사용한다. 외부 입력 시트와 실시간 출결의 기존 연결, 모바일 계약 3·72시간 세션·최소 출결 응답, PC 120시간 세션을 유지한다.

출력 로그는 작업 폴더 `out/migration-*-stage3.log`에 있다. 합성 화면 캡처는 원래 작업 폴더의 `outputs/firebase-migration-20261113/tracking-status-synthetic.jpg`다. 화면의 7건/2건은 시험값이며 운영 측정값이 아니다.

업무 함수 내용 비교 시험은 명시적 원본 접근·잠금 연결만 원래 호출로 정규화하여 기존 업무 로직이 같은지 검사한다. **실제 배포 가드와 배포 스크립트는 수정하지 않았으며 원본 소스 그대로의 차이를 차단한다.** 이 시험 통과가 배포 승인이나 main 검토 완료를 뜻하지 않는다. 실제 배포 전 [프로젝트 규칙](../../AGENTS.md)에 따라 데스크톱 변경을 main에서 검토·검증해야 한다.

## 실제 Google Sheets 시험의 남은 확인

- 별도 프로젝트 [웅천고 Firestore 연결 시험 (운영 분리)](https://script.google.com/home/projects/16HGqhZ9mL-qtcvj9x0lIUrJ49l33xmB8PZgbB-af9BX5HEgonPcp9_x9/edit)에 `probeSheetsChangeTracking`과 모듈을 올렸다. 운영 프로젝트는 업로드하지 않았다.
- 추가 `spreadsheets` OAuth 범위 때문에 Google의 권한 승인이 필요하다. 이전에 완료한 Firestore/외부 요청 승인과 다른 범위다. Chrome에서 권한 검토 화면을 열고 사용자의 승인·시험 실행을 요청한 상태이며 이번 보고 시점에는 완료 응답과 성공 로그를 확인하지 못했다.
- 시험 코드는 고정된 별도 스크립트 ID를 확인하고 합성 자료 문서 하나만 만들거나 재사용한다. 운영 원본·보존 사본 ID를 명시적으로 거부한다. 업무 자료를 열거나 Firestore로 보내지 않는다.
- 생성/수정/삭제·삭제표식·중첩 잠금·같은 ID 중복 요청·내용 충돌·저널 완료를 확인하도록 준비했다. 재실행 시 합성 원본 추가 쓰기 0회가 기대되지만 **실제 Google 환경에서 이 결과를 아직 확인하지 않았다.**
- 원격 시험 업로드 후 로컬 상태 집계의 빈 예약 구간 처리와 UUID 중복 검사를 추가 보완했다. 승인 완료 후 실행 로그를 먼저 확인하고, 최종 모듈을 `scripts/prepare-firestore-probe.ps1`로 다시 올려 동일 시험을 마친다. 실제 네이티브 Apps Script 메서드와 저장 동작 확인을 로컬 모형으로 대체하지 않는다.

## 이어서 할 일

1. 대기 중인 추가 권한 승인·합성 시험 결과를 확인하고 최종 모듈로 반복 실행의 추가 쓰기 0회까지 검증한다. 새 사본이나 Firebase 프로젝트를 다시 만들지 않는다.
2. 운영 활성화 전 모든 쓰기 종류·오래된 요청·진행 중 실행의 경계를 재점검하고, 기존 승인 범위와 배포 규칙에 맞춰 main 검토 및 고정 배포 갱신 절차를 수행한다. 현재 변경은 서비스 62 개발본이며 운영 배포를 시도하지 않았다.
3. 변경 추적 초기화와 `UNG_MIGRATION_TRACKING_V1` 활성화를 안전하게 적용할 관리 절차를 만든다. 기존 비밀번호·세션 속성은 읽어 내보내거나 초기화하지 않는다. 이전 코드로 시작해 실행 중인 요청이 모두 끝나기 전에는 R0 경계를 잡지 않는다.
4. 추적 중 누락이 없는지 확인하고 공통 잠금에서 R0를 얻는다. 기존 보존 사본은 조사용 백업이며 R0가 아니다.
5. 저널 변경분 복제 작업자·불확실 작업 확인/복구·종단 간 일치 검증을 연결한다. 현재 `MigrationSync.gs`는 스냅샷 기반이고 새 저널을 소비하지 않는다. 보존 기간/정리 기능도 아직 가동하지 않았다.
6. 실제 자료 복제, PC·모바일 응답 대조, 전환/복구 리허설을 끝내고 보고한다. **완전 동기화 보고 후 사용자가 운영 전환을 지시할 때만 조회·저장 기준을 변경한다.**

운영 원본 내용·고정 배포·URL·인증 설정·활성 세션은 이번 단계에서 바꾸지 않았다. Spark 유지, 결제·유료 서비스 추가 없음. 비용이나 무료 한도 조사를 매 개발 단계의 중단 조건으로 삼지 않는다.
