# 누적 개선 계획

이 문서는 사용자가 전달한 개선 의견을 시험판 제작 전까지 보관하는 대기 목록입니다.

## 작업 규칙

- 개선 의견 단계에서는 이 문서만 갱신하고 코드·버전·설치파일·배포 상태는 변경하지 않는다.
- 사용자가 시험판 제작을 요청하면 아래 대기 항목 전체를 시험판에 구현하고 검증한다.
- 시험판 제작과 검증이 끝나면 아래 대기 목록을 비운다.
- 사용자가 업데이트 배포를 요청하면 정식 버전 개발과 자동 업데이트 배포 절차를 진행한다.
- 긴급 업데이트가 필요해 보이면 사용자에게 먼저 확인받는다.

### 2026-09-17 모바일 3학년 수강생 출결의 당김·교체수업 연동

#### 목표 동작

- 모바일 `오늘의 교사 시간표`에 최종 반영된 수업이 3학년 수업이면 기본 시간표뿐 아니라 당김수업과 교체(교환)수업에도 `출결 현황` 버튼을 표시한다.
- 출결 버튼과 수강생 명단은 교사 이름이나 화면의 교시만으로 판단하지 않고, 실제로 이동한 `수업 자체`와 그 수업의 수강생 명단을 따라간다.
- 당김수업은 옮겨진 날짜·교시에서 원래 수업의 수강생 출결을 보여준다. 원래 교시를 비우는 이동형 당김은 원래 칸에 버튼을 남기지 않고, 추가 운영형 당김은 원자료의 운영 방식에 따라 두 수업을 각각 표시한다.
- 교체수업은 두 수업의 과목·수강생 묶음이 서로 바뀐 교사와 교시를 따라가게 한다. 따라서 로그인 교사는 교체 후 자신이 실제로 진행하는 3학년 수업의 수강생만 확인한다.
- 3학년 수업과 다른 학년 수업이 교체된 경우에도 3학년 수업이 실제 배치된 칸에만 출결 버튼을 표시한다.
- 취소·거절·보류 상태는 반영하지 않고, 승인 완료 또는 요청자 우선 반영 조건을 현재 모바일 시간표와 동일하게 적용한다.

#### 판정 구조

- 현재 서버 출결 판정이 기본 학생 개인별 시간표와 `일일시간표예외`만 대조하는 구조를 개선해, 모바일에 표시되는 최종 시간표와 출결 판정이 같은 수업 해석기를 사용하게 한다.
- 판정 순서와 충돌 처리 기준을 모바일 시간표와 하나로 통일한다. 기본 주간시간표에 특정 요일 운영·일일시간표예외·승인/반영 교체수업·당김수업을 합성한 뒤 최종 수업을 확정한다.
- 각 최종 수업에 원래 날짜·원래 교시·원래 교사·과목·수업반·강의실·변경 종류를 포함한 내부 `수업 식별자`를 부여하고, 이 식별자로 공유 학생 개인별 시간표에서 실제 수강생을 찾는다.
- 당김수업 최소 색인에는 날짜·교시·교사·과목·수업반·원래 수업 위치만 포함하고, 전체 학생 명렬이나 학생 개인별 시간표를 PWA 정적 파일에 추가하지 않는다.
- 교체와 당김이 같은 칸에 겹치거나 수업 식별에 필요한 값이 부족하면 임의의 학급 명렬을 대신 보여주지 않고 `출결 대상 확인 필요`로 표시한다.
- 동일한 수업이 원래 칸과 이동한 칸에 중복 집계되지 않도록 최종 수업 식별자 기준으로 중복을 제거한다.

#### 서버·PWA 계약과 캐시

- Apps Script가 인증된 사용자와 최종 수업을 확인한 뒤 출결 비고가 있는 실제 수강생의 반·번호·이름·비고와 반별 입력 상태만 최소 응답한다.
- 전체 학생 명렬·전체 학생 시간표·학번·구글시트 원본 응답을 모바일로 전달하지 않는 기존 개인정보 계약을 유지한다.
- 기존 `contractVersion: 3`과 출처별 `sourceStatus`를 유지하고, 호환 가능한 선택 필드로 변경 종류와 원래 수업 위치를 전달한다.
- 실제 구현·배포 때 `MOBILE_SERVICE_VERSION`을 올리고, 승인된 수업 변경 또는 당김 자료의 갱신 시각을 캐시 키에 반영해 변경 직후 오래된 출결 버튼이 남지 않게 한다.
- 출결 자료는 기존처럼 5분 간격으로 다시 확인하고, 출결 시트 조회 실패와 수업 변경 자료 조회 실패를 구분한다. 실패 시에는 출처와 기준 시각이 일치하는 이전 정상 자료만 `이전 자료`로 표시한다.
- 서비스 워커는 Apps Script POST를 캐시하거나 차단하지 않는 기존 원칙을 유지한다.

#### 화면 표시

- 당김 또는 교체가 적용된 출결 버튼에는 기존 상태 문구와 함께 작은 `당김` 또는 `교체` 표시를 추가해 사용자가 명단의 기준을 알 수 있게 한다.
- 상세 창 제목과 안내에는 최종 교시·과목·수업반을 우선 표시하고, 필요할 때만 `원래 ○요일 ○교시 수업`을 보조 문구로 표시한다.
- 반별 입력 전·입력 완료가 섞인 경우와 출결 비고 없음·일부 있음·확인 필요 상태는 기존 색상 체계를 유지한다.

#### 구현·검증 완료 기준

- 기본 3학년 수업, 같은 날 교체, 서로 다른 날짜의 교체, 정규 당김수업, `move_pulled` 일일 예외를 각각 테스트한다.
- 교체 전후 두 교사의 시간표에서 과목과 수강생 명단이 올바른 칸으로 함께 이동하고 원래 칸에 중복 버튼이 남지 않는지 확인한다.
- 당김수업의 출결이 원래 수업의 실제 수강생과 일치하고, 이동형·추가형 처리 차이가 보존되는지 확인한다.
- 취소·거절·보류·승인·요청자 우선 반영 상태와 3학년/다른 학년 교차 교체를 검증한다.
- 변경 자료 누락·중복·충돌 때 다른 학급 학생이 노출되지 않고 `확인 필요`로 안전하게 멈추는지 확인한다.
- 모바일 typecheck, 전체 단위·통합 테스트, 빌드, Code.gs 구문 검사, 실제 고정 주소 로그인·시간표·출결 조회와 금지된 학생 필드 부재를 검증한다.
- 구현 범위는 모바일 PWA와 기존 고정 Apps Script 서비스이며, 데스크톱 설치파일은 별도 데스크톱 기능 변경이 없는 한 다시 만들지 않는다.
- 이 항목은 현재 개선계획만 확정한 상태이며, 사용자가 시험판 제작 또는 업데이트 배포를 명시적으로 요청하기 전에는 코드·버전·배포 상태를 변경하지 않는다.

### 2026-09-17 학생 위치 찾기 요청 차단 오류 및 잘못된 서버 경고 수정

#### 확인된 원인

- 설치된 데스크톱 v1.1.32의 학생 위치 찾기는 `getTimetableOverrides`를 요청하지만, Electron 메인 프로세스의 `HUB_ACTIONS` 허용 목록에 이 요청이 빠져 있어 서버 전송 전에 `허용되지 않는 요청입니다.`가 반환된다.
- 렌더러가 그 로컬 차단 오류를 `학교 공유 서버 업데이트가 필요합니다. 관리자에게 문의하세요.`로 바꿔 표시하므로 실제 원인을 잘못 안내한다.
- 2026-09-17 확인 당시 고정 Apps Script 서비스 버전 47은 `getTimetableOverrides`와 학생 시간표·명렬 등 이 화면의 조회 요청에 정상 응답했다. 따라서 이 오류만을 해결하려고 서버를 새로 배포하거나 학생 자료를 다시 업로드하지 않는다.

#### 수정 범위

- Electron의 `HUB_ACTIONS`에 `getTimetableOverrides`, `saveTimetableOverride`, `deactivateTimetableOverride`를 추가하고, 읽기 요청인 `getTimetableOverrides`는 `HUB_READ_ACTIONS`에도 추가한다.
- 학생 위치 찾기의 필수 자료와 보조 자료 조회를 분리한다. 일일시간표 예외 또는 수업 변경 조회만 실패하면 기본 위치 검색은 유지하되 `변경 수업 정보를 확인하지 못했습니다. 실제 위치를 다시 확인해 주세요.`라는 눈에 띄는 경고를 표시하고 변경 반영 결과를 확정값처럼 안내하지 않는다.
- 로컬 허용 목록에서 차단된 요청은 `프로그램에 필요한 요청이 누락되었습니다.`로 구분하고, 실제 서버가 요청을 거절한 경우에만 서버 호환성 안내를 표시한다. 네트워크 장애·시간 초과도 각각 별도로 안내한다.
- 관리자 일일시간표 예외 조회·저장·비활성화 화면까지 같은 누락의 영향을 점검한다.

#### 재발 방지 및 검증

- 렌더러의 `schoolHub` 요청 액션, Electron `HUB_ACTIONS`·`HUB_READ_ACTIONS`, Apps Script `doPost`·읽기 액션 목록의 대응 관계를 자동 검사에 추가한다.
- 학생 위치 찾기 최초 진입·새로고침·학번 검색·특정 시간 위치찾기를 설치판에서 검증하고, 일일 예외가 있는 날짜와 없는 날짜를 모두 테스트한다.
- 보조 조회 한 건만 실패하는 경우에도 학생 검색은 가능하지만 불확실성이 표시되는지, 서버 정상 응답을 로컬에서 잘못 차단하지 않는지 테스트한다.
- 데스크톱 typecheck 및 관련 테스트를 통과한 뒤 다음 시험판 또는 정식 업데이트에 포함한다. 현재는 계획만 기록하며 코드·설치파일·배포 상태는 변경하지 않는다.
