# 웅천고 업무도우미 Firebase 이전 상세계획

- 작성일: 2026-11-10
- 단계: **2. 상세계획 작성 완료 / 개발·실제 동기화·운영 전환 전**
- 사용자 결정: Firebase로 이전하되 무료 운영을 우선한다. 현재도 교직원이 사용하므로 기존 서버를 유지하고, 완전 동기화와 검증을 마친 이후 전환한다.
- 이번 실행 범위: 계획·대기 목록 저장만 수행한다. Firebase 프로젝트 생성, 결제 연결, 권한 변경, 원본 데이터 내보내기, 트리거 설치, 운영 코드·배포 변경은 수행하지 않는다.
- 코드 조사 기준: origin/main `80f12b01`, PC 설치본 1.1.40, 공유 서비스60. 과거 문서의 서비스53 등은 당시 기록이며 이번 설계의 최신 기준이 아니다. 실시간 자료 총량·실제 접속량은 아직 측정하지 않았다.

## 1. 목표와 이전 범위

**기존 서비스 계속 사용 → Firebase 복제본 구축 → 운영 중 변경분 추적 → 같은 시점의 데이터/동작 일치 확인 → 저장 기준 전환** 순서로 진행한다.

“완전히 동기화”는 단순히 행 수가 같은 상태가 아니다. 확정된 기준 시점까지 생성·수정·삭제·대량 교체가 모두 반영되고, ID·순서·연결 관계·권한·업무 상태·실제 조회 결과가 일치하는 상태로 정의한다.

무료 Spark는 Firestore를 사용할 수 있지만 Cloud Functions와 Firebase Cloud Storage까지 같은 무료 구성에 포함되는 것은 아니다. 따라서 1차 목표는 **학교 공유 DB를 Firestore로 이전하고 기존 Apps Script는 인증·업무 API·시트 연계 창구로 유지**하는 것이다. 앱과 모바일의 기존 공개 주소와 통신 계약을 지킨다.

- 이전 완료라고 표시할 범위: 승인된 학교 공유 데이터의 주 저장소와 해당 조회/저장 처리.
- 유지하는 범위: Apps Script API·현재 로그인 세션/비밀번호 검증·외부 입력 시트 연결·기존 비공개 자료집 파일 제공.
- Apps Script 완전 폐기와 Firebase 단독 인증/API 전환은 2차 별도 설계 대상이다. 현재 “이름+공통 비밀번호”와 서버의 승인·조회 로직을 그대로 없애면서 Spark만으로 대체할 수 있다고 약속하지 않는다.
- 중간 API를 유지하므로 모든 지연·학교망 접속 문제가 자동 해결되는 것은 아니다. 실제 전후 응답시간과 프록시 환경을 비교한다.

## 2. 유지할 사용자 경험과 보호 조건

1. 동기화 준비·초기 복사·병행 검증 중 기존 앱과 모바일을 계속 사용한다. Firebase 작업 실패가 현재 저장을 실패로 바꾸지 않도록 한다.
2. 최종 전환에서는 조회는 계속 제공하고 저장만 잠시 대기/재시도할 수 있는 경계를 마련한다. **무제한 동시 저장과 순간적인 0지연 완전 일치를 동시에 보장하지 않는다.** 목표 대기 시간은 1~3분 이내로 잡고 실제 사전 리허설에서 확인한다. 초과하면 전환을 취소하고 기존 저장을 재개한다.
3. PC 120시간, 모바일72시간, 교장·교감 별도 인증과 우수사례 추가 잠금을 유지한다. 현재 유효한 세션·기존 공통 비밀번호 ScriptProperty를 초기화하지 않는다.
4. 교직원 명렬의 등록 순서·ID·직책과 명렬 외 추가 로그인 허용을 분리해 보존한다. 로그인 허용자를 명렬에 자동 삽입하지 않는다.
5. 학생부·내신등급 산출기 원본/성적·개인 로컬 업무·API 키 등 기존 로컬 자료를 새 DB에 자동 업로드하지 않는다.
6. 구버전 PC도 기존 고정 API를 통해 같은 저장소로 연결한다. 구버전과 새 버전이 서로 다른 DB를 독립 수정하는 구성을 금지한다.
7. 전환은 사용자에게 동기화/검증 보고서를 보여준 뒤 실제 전환 지시를 받아 진행한다. 이번 계획 요청을 즉시 운영 전환 승인으로 해석하지 않는다.

## 4. 무료 운영 구성과 접근 제어

### 4.1 기본 구성

```text
PC 정식 앱 · 구버전 앱 · 모바일 PWA
             ↓ 기존 HTTPS API / 기존 인증
기존 고정 Apps Script (호환·권한 검증·업무 처리)
             ↓ 서버 전용 Firestore REST / OAuth + IAM
     Firebase Spark · Cloud Firestore Standard
             ↕ 이전 모드에 따른 단일 방향 복제
기존 학교 공유 구글시트 · 외부 입력 시트 · 비공개 파일 보관
```

- 후보 리전: 서울 `asia-northeast3`. 프로젝트 소유·학교 계정 관리·기존 GCP 연결·위치 선택 제약을 프로젝트 생성 전에 확인한다.
- 결제 계정을 연결하지 않는 Spark 구성을 기본으로 한다. Cloud Functions, Cloud Run, Firebase Cloud Storage, 유료 자동 백업/PITR, 유료 관리형 export/import를 전제로 구현하지 않는다.
- 초기 개발은 Emulator와 합성 데이터로 수행한다. 운영 자료를 공개 테스트 DB에 올리지 않는다.
- 기존 API 실행 계정에 필요한 Firestore IAM 권한만 부여하고 서버에서 단기 OAuth 토큰으로 호출하는 경로를 먼저 시험한다. Apps Script 권한 범위·실행 소유자 승인·GCP 프로젝트 연결을 검증한다. 앱에 서비스 계정 키를 넣지 않는다. 새 권한은 운영용 함수에 붙이기 전에 별도 시험 함수로 검증하여 로그인 전체 재승인 장애를 막는다.
- IAM 서버 요청은 Firestore Security Rules와 별도 권한 체계다. 따라서 서버가 세션·교사·관리자·본인 자료 권한을 매 요청 검증한다. 이름·역할을 클라이언트 본문에서 받았다는 이유만으로 신뢰하지 않는다.
- 1차에서는 브라우저/PC의 Firestore 직접 읽기·쓰기를 Rules에서 기본 거부한다. Rules를 public/test mode로 열지 않는다. 서버 요청의 IAM과 앱 권한 테스트를 각각 수행한다.
- 2차 Firebase Authentication을 검토한다면 고정 UID·기존 이름 대응·허용 취소·공통 비밀번호 변경·세션 정책을 별도 설계한다. 익명 로그인 후 클라이언트 이름값으로 권한을 주지 않는다.

### 4.2 무료 한도와 읽기 비용 절감

2026-11-10 공식 Standard 기준: DB 1GiB, 읽기50,000/일, 쓰기20,000/일, 삭제20,000/일, 외부전송10GiB/월. 이는 신규/기존 이용·동기화·검증·백업을 합친 프로젝트 전체 한도다. 단순 HTTP 요청1회가 문서 읽기1회를 의미하지 않는다.

- `getSyncManifest`를 가벼운 버전 문서로 유지한다. PC 위젯/모바일이 변하지 않은 전체 시간표를 반복 읽지 않는다.
- 날짜·본인·담당 범위만 조회, 적정 페이지 크기, 필요한 인덱스, 서버 캐시와 기기 캐시를 사용한다. 전체 데이터 실시간 구독은 사용하지 않는다.
- 예시 추정: 66개 기기가8시간 동안5분마다 버전 문서2개를 각각 읽는다면 `66×96×2=12,672` 읽기/일이다. 각 회차에100개 문서를 읽으면 `633,600`으로 무료 한도를 넘을 수 있다. 실제 활성 사용자 수는 아직 측정하지 않았으며 이 계산은 설계 예시다.
- 초기 복사와 전수 대조·논리 백업은 페이지별 체크포인트를 두고 서비스 사용량을 포함해 실행량을 계획한다. 한도 밖 무료 기능으로 간주하지 않는다. 자료가 많으면 며칠에 나눠 복사한다.
- 권장 내부 여유 목표: 총 읽기30,000/일 이하, 쓰기10,000/일 이하, 저장700MiB 이하. 무료 한도 자체와 구분한 초기 설계 목표이며 실제 자료량으로 조정한다.
- Spark는 한도 초과 시 기능이 제한될 수 있다. 결제 등록 없이 사용량 측정과 부족 경고를 구현하되 비용 때문에 사용자 기능을 임의 축소하거나 요금제를 자동 전환하지 않는다.
- Apps Script 실행시간·URL Fetch·트리거 한도도 별도로 확인한다. 서버 전체를 매분 읽는 트리거를 만들지 않는다.

## 5. 데이터 키·변경 이력·스키마

- 학교 고정 범위 `schools/{schoolId}` 아래 리소스를 분리하고 기존 ID를 보존한다. 이름·행 번호·정렬 위치를 문서 ID로 쓰지 않는다.
- 원본 ID가 없으면 최초 대응표를 만들고 유지한다. 66명 등 현재 건수는 기준일의 관측값이며 향후 인원 변동을 오류로 간주하지 않는다.
- 학생 학번과 교실·시간은 문자열/정의된 타입으로 변환하며, 원본 0·빈 문자열·null·날짜·논리값 구분을 명세한다. 학년·반·번호는 별도 필드로 보존한다.
- 공통 메타: `schemaVersion`, `sourceId`, `resourceRevision`, `updatedAt`, `payloadHash`, `isDeleted`, `migrationRunId`. 로그에는 학생 이름·성적·출결 비고·토큰을 넣지 않는다.
- 영구 삭제 대신 동기화 기간에는 삭제표식(tombstone)을 사용한다. 재복사로 삭제 자료가 부활하지 않도록 삭제도 일반 변경과 같은 순서로 적용한다.
- 대량 시간표/명렬 교체는 revision별 새 묶음 작성→건수/해시/참조 검증→활성 revision 전환 순서로 처리한다. 전체 자료를 거대한 문서1개로 저장하지 않는다. 문서1MiB 한도를 고려해 분할한다.
- 운영 제어: `migration/control`의 mode/epoch/activeBackend/검증된 revision을 관리한다. 명시적 상태는 `SHEETS_PRIMARY` → `MIRRORING` → `VERIFIED` → `CUTOVER_PENDING` → `FIRESTORE_PRIMARY`이며 복구는 별도 `ROLLBACK_PENDING`을 거친다.
- 작업 기록은 `operationId`, `resource`, `sourceRevision`, `operationType`, `targetId`, `status`, `attempt`, `lastErrorCode` 등을 가진다. 복제 이벤트 본문에 개인정보가 필요하면 비공개 보관하고 짧은 보존정책을 정한다.

## 6. 운영 중 동기화 방법

### 6.1 단일 저장 기준

전환 전 **구글시트가 유일한 원본**이다. Firebase는 검증용 복제본이며 사용자에게 쓰기 권한을 열지 않는다. PC가 양쪽 서버에 각자 저장하는 이중 쓰기를 구현하지 않는다.

기존 API의 생성·수정·삭제·엑셀 업로드·NEIS 동기화·수업 승인·시트 초기화/보정 등 모든 쓰기 경로를 먼저 목록화한다. 현재 버전 표시(`touchSyncResource`)가 없는 공유링크·공지·위원회 변경까지 추적해야 한다.

### 6.2 변경 로그와 실패 복구

1. 변경 요청의 권한을 검증하고 `operationId`를 정한다. 신규 앱은 클라이언트 요청ID를 보내고 서버는 이를 검증·보관한다. 구버전은 서버 생성ID로 기록하되 자동 재요청의 중복 판정 한계를 명시한다.
2. 관련 쓰기를 공통 잠금/순서 체계에 넣고 변경 의도·대상·예정 revision을 비공개 로그에 먼저 남긴다. 기록에 실패하면 실행 전 실패로 돌려주며 성공으로 표시하지 않는다.
3. 현재 원본인 시트 변경을 실행하고 실제 변경 후 행/리소스 해시를 기록한다. **시트 변경과 로그 기록은 하나의 DB 트랜잭션이 아니므로**, 실패 단계별 복구 분기를 구현한다.
4. 복제기가 해당 revision을 Firestore에 반영한다. `operationId` 기반 중복 억제와 이전 revision 거부로 여러 번 받아도 같은 결과가 되도록 한다.
5. Firebase만 실패하면 `pending`으로 남겨 지수 백오프·횟수 제한·관리자 재실행으로 복구한다. 기존 시트 저장 성공을 취소하지 않는다.
6. 로그만 기록되고 원본 적용이 불명확하면 ID/현재 원본 revision을 먼저 확인한다. 생성/승인을 무조건 재실행하지 않는다. 불명확한 구버전 요청은 확인 대상으로 분리한다.
7. 로그 누락 가능성을 닫기 위해 원본과 복제본의 정기 해시 대조를 병행한다. 최소 한 번 처리+멱등 재적용 방식이며 정확히 한 번 전송을 보장한다고 표현하지 않는다.

### 6.3 초기 복사 중 변경을 놓치지 않는 절차

- 먼저 변경 추적 경로를 배포하고 시험한다. 그 후 기준 revision `R0`를 정하고, 짧은 리소스 잠금에서 불변 스냅샷을 만든다. 이후 사용자 저장은 원본에 계속 허용하고 변경 로그를 축적한다.
- 대형 자료의 스냅샷 생성이 길면 기존 업로드 revision을 활용하거나 리소스별 짧은 관리자 업로드 대기를 공지한다. 페이지별 원본이 바뀌는데도 하나의 일관된 스냅샷이라고 간주하지 않는다.
- `R0` 스냅샷을 페이지 단위로 복사한 뒤 `R0` 이후 생성/수정/삭제를 순서대로 적용한다. 늦게 도착한 초기 복사가 새 변경을 덮어쓰지 못하게 revision 조건을 둔다.
- 사용자 사용 중에는 확정된 같은 기준 revision의 스냅샷/로그 결과를 비교한다. 서로 다른 시각의 살아 있는 시트와 DB를 비교해 오탐을 만들지 않는다.

### 6.4 시트 직접 편집·외부 프로그램

- onEdit/onChange만으로 전체 변경이 잡히지 않는다. Apps Script 실행·API 수정은 편집 트리거를 발생시키지 않을 수 있다.
- 시트 직접 편집/외부 연계마다 작성 주체와 소유 리소스를 지정한다. 편집 이벤트의 dirty 표시와 주기적인 범위별 해시 스캔을 함께 사용한다. 외부 자동화는 가능하면 동기화 API로 합친다.
- 외부 입력 시트는 계속 원본으로 두고 `sourceRevision/sourceHash/fetchedAt`를 기록한다. 행 이동·삭제·수식 결과 변경·날짜 열 변경도 검사한다. 동기화 지연 목표는 업무시간5분 이내이며 자동화 트리거 오차를 감안해 실제 지연을 측정한다.
- 내부 DB 대상 시트의 직접 편집은 전환 시점에 관리 절차로 잠시 중지하고, 전환 후에는 조회용 사본으로 취급한다. 외부 입력 시트와 혼동하지 않는다.
- 통제할 수 없는 쓰기 경로가 남아 있으면 “전부 동기화됨”으로 판정하지 않고 해당 리소스는 시트 원본을 유지한다.

| 0. 조사/백업 | 기존 시트 | 전체 탭·쓰기 action·직접 편집·외부 연결·건수/바이트 조사, 원본 비공개 사본 | 누락 없는 데이터/동작 목록·복구 사본 |

| 4. 운영 병행 검증 | 기존 시트 | 실제 변경 복제, Firebase 응답을 사용자에게 반환하지 않는 비교 조회 | 최소5개 실제 업무일 권장, 동작 차이/미처리 로그 없음 |
| 5. 읽기 전환 시험 | 저장은 시트 | 관리자/시험 계정에 같은 revision의 Firebase 읽기 허용 | 모바일/PC/위젯 결과 일치, 저장 직후 읽기 보장 |
| 6. 최종 전환 | 사용자 승인 후 Firestore | 저장 잠시 대기·최종 R* 일치·원본 저장권한 차단·epoch 전환 | 명시한 전환 관문 전부 통과 |

| 8. 기존 저장 정리 | Firestore | 최소30일 원본 보관 제안, 종료 조건 보고 | 사용자 확인 후에만 후속 정리 |

기간 예시: 구현/사전 시험 약5~8업무일 + 운영 병행 최소5업무일 + 안정화5업무일. 실제 범위·자료량에 따라 조정한다. 날짜가 지났다는 이유로 미일치 자료를 남긴 채 전환하지 않는다.

읽기 전환 시험은 최소 클라이언트/서버 영역에서만 한다. 특정 학생에게 다른 revision의 시간표를 주는 혼합 읽기를 하지 않는다. 시트 저장 직후 Firestore 복제가 끝나지 않았으면 시트에서 읽거나 명시적 동기화 대기로 처리한다.

## 8. 관리자 진행 화면/검증 보고서

계획 단계의 화면 요구이며 아직 구현되지 않았다.

- 현재 저장 기준: 구글시트 / Firebase / 전환 대기.
- 표: 자료 종류, 원본 수, 복제 수, 삭제표식 수, 기준 revision, 필드 해시 일치, 최근 정상 동기화 시각, 대기 건수, 오류 건수.
- 별도 상태: 초기 복사 중 / 변경분 반영 중 / 원본 확인 필요 / 재시도 필요 / 비교 일치 / 전환 가능.
- “초기 복사100%”와 “전환 준비 완료”를 분리한다. 전체100%는 대상 범위와 기준 시각을 함께 표시한다.
- 동작: 수동 동기화, 실패 건 재검증, 결과 보고서 저장. 전환은 권한 있는 관리자 전용이며 자동 시간표/캐시 작업이 임의 실행하지 않는다.
- 로그는 건수·리소스 코드·revision·오류 코드 중심이다. 이름·학생 식별정보·성적·원본 자료집·비밀번호·토큰을 공개 보고서나 화면 캡처에 노출하지 않는다.
- 사용량 표시와 실패 안내를 실제 구성한 뒤 검증한다. 현재 상시 감시/알림이 이미 켜져 있다고 보고하지 않는다.

## 10. 최종 전환 절차

1. 관리자에게 대상·전수 대조·미해결 오류·사용량·예상 저장 대기시간·복구 결과를 보고한다. **동기화 완료 후 사용자의 실제 전환 지시**를 받는다.
2. 기존 쓰기 action/관리자 업로드/NEIS 저장/자동화 작업을 같은 전환 잠금/epoch 경계로 묶고 새 작업을 잠시 대기시킨다. 진행 중 저장을 먼저 완료한다. 조회는 마지막 정상 버전으로 계속 제공한다.
3. 큐잉이 구현된 신규 요청은 operationId와 “처리 대기” 상태를 제공하며 원본에 반영되기 전에 “저장 완료”로 표시하지 않는다. 대기를 지원하지 않는 구버전에는 명확한 일시 재시도 응답을 주며, 임의의 클라이언트 자동 재전송으로 중복 생성하지 않는다.
4. 내부 대상 시트 직접 편집과 연계 쓰기를 함께 멈추고 최종 기준 `R*`를 확정한다. 마지막 변경분·삭제표식을 모두 반영한다. 대량 업로드 staging도 완료/취소를 확정한다.
5. `R*`에서 대상 ID·값·순서·참조·활성 revision이100% 일치하고 미처리/불명확 로그0건인지 확인한다. 시계가 같다는 것만으로 동일 상태로 간주하지 않는다.
6. 미일치면 즉시 기존 시트 저장을 재개하고 Firebase를 검증본으로 둔다. 정상 사용을 유지하며 원인을 수정한다.
7. 일치하면 중앙 저장 기준과 epoch를 Firestore로 바꾼다. 기존 API의 모든 저장 경로가 이를 따라가게 하고, 이전 epoch 작업이 시트로 늦게 저장하지 못하도록 재검증한다. 관련 리소스의 포인터 전환은 한 묶음으로 처리한다.
8. 대기한 유효 작업을 새 저장소에 멱등 처리하고, PC/모바일/위젯의 자료 캐시 키를 갱신한다. 인증 세션은 초기화하지 않는다.
9. 실제 저장/수정/승인/조회와 구버전 요청을 확인한다. Firestore 연결 실패 때 **쓰기 원본을 자동으로 시트로 되돌리지 않는다.** 마지막 정상 캐시 조회와 저장 실패/대기를 명확히 안내한다.
10. 완료 보고에 전환 시각·R*·대상 범위·검증 결과·구버전 호환·남긴 시트/파일/인증 창구를 명시한다.

전환 관문: 미처리0 / 오류0 / 불명확 작업0 / 대상 전수 일치 / 구버전·모바일·권한 시험 통과 / 저장 대기 리허설 통과 / 복구 가능 / 사용자 전환 지시. 스캔 불가능한 직접 편집 또는 원인 불명 불일치가 남으면 전환하지 않는다.

## 11. 전환 후 동기화·백업·복구

### 11.1 양방향 충돌 방지

- 전환 후 내부 데이터는 **Firestore만 원본**이다. 시트는 Firestore→시트의 복구/조회 사본으로 단방향 갱신하고, 동일 리소스에 시트→Firestore 동기화를 동시에 켜지 않는다.
- 외부 입력 시트는 해당 별도 리소스의 원본으로 계속 유지한다. 리소스마다 sourceOfTruth를 지정해 복제 루프를 차단한다.
- Firestore의 승인·이력·operationId·revision 갱신은 가능한 범위의 트랜잭션/원자 commit으로 묶는다. 재시도되는 트랜잭션 안에서 외부 시트 쓰기/파일 전송을 실행하지 않는다. 별도 작업 로그로 후처리한다.

### 11.2 무료 백업

- 초기 원본 사본과 전환 R* 자료를 비공개 보관한다. 이후 변경 로그와 정기 논리 스냅샷(JSON 등)을 별도 비공개 위치에 저장한다. 문서 ID·타입·순서·삭제표식·스키마를 포함한다.
- Spark에서 유료 관리형 export/import·PITR가 자동 제공된다고 가정하지 않는다. 일반 REST 읽기 기반 논리 백업 도구를 구현하고 복원 시험을 한다. 백업 읽기도 무료 한도에 포함한다.
- 제안 주기: 변경 로그는 계속 기록, 업무일 종료 시 증분 백업, 전환 직전/중요 업로드 전 전체 논리 백업, 주1회 전체 백업은 자료량을 보고 결정한다. 실제 스케줄을 구성하기 전에는 자동 백업 중이라고 보고하지 않는다.
- 학생 개인정보 포함 백업은 암호화·관리자 한정 접근·보존 기간 지정. 초기 원본 최소30일 보존을 제안하며 자동 삭제는 이번 계획으로 승인하지 않는다.

### 11.3 복구

- 전환 전: 시트 운영 그대로, 복제 오류 수정 후 이어서 동기화. 사용자 원본을 복제본으로 덮어쓰지 않는다.
- 전환 후: 새 저장을 잠시 대기 → 진행 작업 완료 → Firestore 최종 확정 revision/로그 백업 → R* 이후 변경을 시트에 전부 반영 → 같은 시점 전수 대조 → epoch를 바꿔 시트 원본으로 복귀 → 대기 작업 재개.
- 역방향 복제 대기/오류가 있으면 즉시 시트로 돌리지 않는다. “버튼 한 번으로 무조건 데이터 손실 없는 복귀”라고 약속하지 않는다.
- 목표: 사용자가 성공 응답을 받은 저장의 손실0건. Firestore 장애로 최신 확정 자료를 읽을 수 없으면 이 목표를 보장할 수 없으므로 복구를 강행하지 않고 조회 가능한 캐시/마지막 검증본과 저장 대기 상태를 안내한다.

## 12. 구현 파일과 결과물

실제 이름은 개발 시 확정한다.

- server: 기존 Code.gs·StaffAuth.gs 인증/정책 유지, 새 FirestoreRepository.gs(REST/타입/transaction), MigrationSync.gs(로그·복제·대조), MigrationAdmin.gs(권한·상태·전환), 소스별 읽기/쓰기 어댑터.
- Firestore: rules 기본차단, 인덱스, schemaVersion, 리소스 manifest, operation 로그, 활성 revision, migration control/epoch. 서비스 계정/토큰/원본 자료는 Git 제외.
- PC: 기존 schoolHub 계약·staff-transport 유지, 관리자 동기화 진행/검증 화면, 필요 시 operationId·대기 상태·캐시 revision 갱신. 메뉴/흐름 변화는 workAssistantSearch도 갱신.
- 모바일: 기존 api/types/세션/캐시/contractVersion3 보존. 일반 일정만 조회하고 출결 상세 장기 보관 금지.
- 검사: Emulator/합성 자료 기반 권한·트랜잭션·중복·지연·삭제·대량 교체·역복제, 기존 typecheck/모바일 전체 테스트/배포 가드, 실제 Windows·학교망 검증.
- 결과물: 원본 목록/매핑표, 작업별 체크포인트, 무결성 보고서, 동기화 현황, 실패/재시도 기록, 무료 한도 측정, 전환/복구 리허설 보고서, 원문 개인정보 없는 사용자 안내.
- 서버 변경 배포는 최신 main/원격 HEAD/고정 배포 비교 후 `npm run deploy:apps-script`만 사용한다. 기존 보호 함수의 의도적 변경은 검토·테스트·main 반영 절차를 거치며 가드를 우회하지 않는다. 최초 변경 추적 배포도 사용자가 지시한 개발/배포 단계에서 수행한다.
